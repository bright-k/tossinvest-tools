# 인증과 주문 처리

토스 비밀을 모델에 전달하지 않는 것과 주문 권한을 제한하는 것을 함께 구현합니다. 모든 쓰기는 서버가 인증된 주체, 고정된 작업 내용, 사용자 승인과 현재 계좌 상태를 확인한 뒤 수행합니다. 이 계약은 MCP·CLI·관리 API에 동일하게 적용합니다.

## 신뢰와 인증 경계

| 경계 | 인증과 권한 |
|---|---|
| AI 또는 CLI → 서버 | 토스 비밀과 다른 접속 자격증명. 서버가 주체·허용 계좌·기능을 해석한다 |
| 소유자 → 설정·승인 | AI의 도구 접속 권한과 별개인 사용자 인증·현재 작업 승인 |
| 서버 → 토스 REST·WS | 토스 Client Credentials 토큰과 필요 시 서버가 해석한 계좌 헤더 |

실계좌 연결에 필요한 client_id·client_secret은 사용자가 로컬 입력 흐름으로 저장합니다. 명령 인자·셸 history·Git·채팅을 사용하지 않습니다. Keychain adapter는 서비스 이름·접근 제어·자동 재시작 동작을 검증하고, 비밀을 프로세스 목록이나 디버그 출력에 노출하는 저장 방식을 피합니다. 잠긴 Keychain에 대해 실패를 표시하며 평문 파일로 자동 우회하지 않습니다.

MCP 접속에는 최소 권한을 부여합니다. 소유자 정책 변경·쓰기 활성화·승인 생성·토스 키 읽기는 MCP 도구로 제공하지 않습니다. MCP에서 pause를 허용하더라도 재개·한도 상향·자격증명 변경 권한을 자동으로 부여하지 않습니다.

R1의 초기 주체·scope와 빈 계좌 허용 집합은 [계좌 선택 계약](interfaces.md#계좌-선택과-접속-권한)을 따릅니다. 소유자의 `setup accounts`만 UID를 검증한 Unix socket으로 허용 관계를 바꾸며 TCP 관리 API·MCP에는 계좌 허용 변경 경로를 만들지 않습니다. 매핑·grant·access_revision은 원자적으로 커밋하고 응답 반환·이벤트 페이지에서도 최신 권한을 검사합니다. readonly의 로컬 계좌 선택은 실주문 승인과 별개이며 같은 UID의 셸을 막는 보안 경계로 설명하지 않습니다.

미확인 주문 ID의 조회는 허용 계좌를 지정한 단건 GET만 허용하고 다른 계좌 fallback을 금지합니다. 확인된 타 계좌 관계는 사전 거부하며 404를 소유 관계 증거로 사용하지 않습니다. 쓰기는 ID 관계 확인·fresh 상태·승인을 별도로 요구합니다. 계좌 제한 전제·오류와 충돌 격리는 [ID 계약](interfaces.md#주문-id와-계좌-소유-관계)에 고정합니다.

mock도 접속 인증을 생략하지 않습니다. [mock credential](interfaces.md#mock-접속-credential)은 OS 난수로 실행마다 생성하고 mock 전용 0600 파일에만 둡니다. 토스 SecretStore·Keychain·실제 접속 credential은 읽지 않으며 backend 간 credential·DB 재사용을 금지합니다. 실제 토스 키와 실제 MCP credential의 평문 파일 fallback은 계속 금지됩니다.

CLI가 호출하는 업무 API도 인증을 검증합니다. CLI라는 이유로 승인 없이 매매하지 않습니다. 같은 OS 사용자 아래에서 Codex가 코드·파일·프로세스에 접근할 수 있다면 Keychain만으로 강한 격리가 성립하지 않습니다. 실주문 활성화 전에 별도 서비스 계정 또는 독립 호스트와 사용자 확인 수단을 결정합니다.

## 로컬 HTTP

- loopback에만 바인딩하고 Host와 Origin을 허용 목록으로 검증합니다. CORS를 인증 수단으로 사용하지 않습니다.
- MCP의 각 요청에 주체와 권한을 확인합니다. 세션 ID가 인증정보를 대신하지 않습니다.
- 로컬 승인 화면은 독립 사용자 세션과 CSRF 방어를 사용합니다. 모델이 가진 MCP 토큰으로 승인을 생성할 수 없어야 합니다.
- health 응답에는 비밀·계좌·주문 정보를 넣지 않습니다. 상세 진단은 인증 뒤에 둡니다.
- 원격 접속과 공개 터널은 초기 범위에 없습니다. 추가할 때 HTTPS와 OAuth 등 위협 모델을 ADR로 갱신합니다.

## 실행 프로필과 정책

`serve` 기본값은 readonly이며, 소유자가 `--mode=trading`을 명시한 프로세스에만 선택적 주문 모듈을 포함합니다. mock는 별도 backend입니다. 도구 등록·서비스·실제 전송에서 같은 프로필을 검사하며, 정확한 옵션·재시작·노출 표는 [실행 프로필](runtime-profiles.md)을 따릅니다.

readonly에서는 주문 준비·실행뿐 아니라 승인 라우트·모드 승격도 제공하지 않습니다. Keychain 등록과 토큰 발급·구독·로컬 캐시는 허용되는 운영 동작이며 실제 계좌 쓰기와 구분합니다. 이전 trading DB를 readonly에서 복구하더라도 실제 제출·재시도는 하지 않습니다. R1·R2는 승인 서비스와 실주문 격리의 구현을 기다리지 않습니다.

키 존재를 `trading` 활성화 조건으로 삼지 않습니다. 모드·허용 계좌·종목·시장·호가 방식·한도는 소유자가 관리합니다. 미설정 한도를 무제한으로 해석하지 않고 실주문을 거부합니다. 고액 확인 플래그는 서버가 승인된 금액과 정책을 확인한 뒤 파생시키며, 모델 입력만으로 설정하지 않습니다.

한도는 미체결·전송 미확정·실행 대기 예약을 포함합니다. 동시 요청이 각자 잔고 검사를 통과해 총 한도를 넘지 않도록 승인 소비와 예약을 원자적으로 처리합니다. 주문 수량·금액·가격은 원본 제약을 검증하며, 시장가 금액을 확정할 수 없을 때는 예산·수량 상한을 검증할 수 있는 정책이 필요합니다. 검증 가능한 상한이 없으면 거부합니다.

시장가 수량 주문의 사전 예상 금액은 최종 체결 금액의 보장이 아닙니다. 확정 상한과 추정 노출을 정책·표시에서 구분합니다. 엄격한 체결 금액 상한이 필요한 정책에서는 그 조건을 보장할 수 없는 주문을 거부하며, 승인받은 시장가를 지정가로 몰래 바꾸지 않습니다. 금액·수량 방식의 실제 보장은 해당 시장의 원본 계약을 따릅니다.

## 초안과 승인

1. 요청을 허용된 행동으로 정규화합니다. 대상 계좌·종목·시장·통화·수량 또는 금액·가격·TIF·조건·만료·정정/취소 대상 ID를 확정합니다.
2. 상태·잔고·미체결·시세·장 운영·종목 제한·비용과 정책을 검사합니다. 추정치는 추정이라고 표시합니다.
3. 작업 내용을 변경 불가능한 초안으로 저장하고 canonical hash를 계산합니다. `draft_id`, 승인 만료, 정책 버전과 사전 조회 시각을 연결합니다.
4. 사용자에게 정확한 내용을 표시하고 독립 인증된 승인 흐름에서 동의를 받습니다. 초기 사용자 인증 방식은 실주문 개발 전에 ADR로 결정합니다.
5. 실행 도구는 `draft_id`를 받아 서버의 승인 증거를 조회합니다. 계좌·내용 해시·주체·만료·정책 버전·이미 사용됐는지를 검증합니다.
6. 최신 계좌 상태와 정책을 다시 확인하고 실행 예약과 승인 소비를 커밋한 뒤 전송합니다.

가격·수량·종목·조건·대상 ID 변경, 정책 변경으로 인한 의미 변화, 초안 만료 또는 사전 상태의 중요한 변화는 재검토·새 승인을 요구합니다. 같은 초안의 안전한 전송 재시도는 새 주문 승인과 구분합니다. 고정 금액의 US 시장가 주문도 체결 가격·수량을 약속하지 않습니다.

`confirm=true`, `approved=true`, 도구 설명, 뉴스·오류 메시지의 지시문과 모델이 반복한 자연어는 승인 증거가 아닙니다. 도구 호출 승인 UI도 초안 해시와 서버가 검증한 사용자 신원에 연결되지 않으면 주문 승인 증거로 사용하지 않습니다.

## 로컬 상태와 토스 상태

로컬 작업 상태와 토스 주문 상태를 서로 다른 필드에 저장합니다.

```text
draft → awaiting_approval → approved → dispatching
                                 ├→ expired / invalidated
dispatching → acknowledged → 토스 주문 상태 추적
            ├→ rejected
            └→ outcome_unknown → reconciling → acknowledged / rejected / manual_review
```

전송 전 기록과 네트워크는 원자적이지 않으므로, 재시작 시 `dispatching`도 결과 확인 대상입니다. HTTP 성공은 체결 완료가 아닙니다. 로컬 `rejected`는 토스가 명시적으로 요청을 거부한 경우 등 결과를 확정할 수 있을 때만 사용합니다. 타임아웃·연결 리셋·애매한 5xx를 실패 확정으로 바꾸지 않습니다.

토스의 `PENDING`, `PARTIAL_FILLED`, `FILLED`, `PENDING_CANCEL`, `PENDING_REPLACE`, `CANCELED`, `REPLACED`, 거부 상태를 원문과 함께 보존합니다. 미지의 상태를 임의로 체결·종료 상태로 분류하지 않습니다. 취소·거부·정정 종료에도 부분 체결이 있을 수 있으므로 체결 수량을 유지합니다.

## 생성 재시도와 중복 방지

공식 일반 주문의 `clientOrderId`는 10분 유효합니다. 조건주문 생성의 명세는 일반 생성과 동일한 멱등키 동작을 설명합니다. 일반 생성과 조건 생성 모두 서버가 최초 전송 전에 식별자와 최종 본문을 기록하고 동일한 키·내용으로만 재시도합니다. 실제 재시도 판단은 각 endpoint의 고정 명세를 따릅니다.

- 원래 시도 시작 시각과 보수적인 재시도 마감 시각을 영속 저장합니다. 10분 경계에 여유를 두고 OS 시각 변화도 감안합니다.
- `409 request-in-progress`는 미확정 진행으로 관리합니다. 다른 ID로 우회하지 않습니다.
- 동일 키·다른 내용 충돌은 자동으로 내용을 고쳐 재제출하지 않습니다.
- 유효시간이 지나면 같은 ID도 새 주문이 될 수 있습니다. 이후 자동 재전송하지 않고 조회·사용자 검토로 전환합니다.
- 조회에서 식별자가 확실하게 매칭되지 않으면 유사한 종목·수량만으로 제출 성공이나 실패를 확정하지 않습니다.
- 프로세스 재시작·도구 재호출·MCP 타임아웃에도 같은 초안과 전송 기록을 사용합니다.

로컬 작업의 재호출은 기록된 결과를 반환하거나 복구를 이어갑니다. 새 초안이나 식별자를 은밀히 생성하지 않습니다. 정책 노출 예약은 결과가 확인될 때까지 보수적으로 유지하며, 이중 예약·조기 해제를 검증합니다.

## 정정과 취소

일반 정정·취소에 생성 API와 같은 멱등성을 가정하지 않습니다. 응답을 잃으면 원주문 상태와 관련 주문을 조회합니다. `already-filled`·`already-canceled` 등은 구체적인 결과를 확인한 뒤 반영합니다. 승인 이후에도 토스에서 체결이 진행될 수 있으므로 요청 성공 여부와 최종 체결 수량을 따로 확인합니다.

조건주문 수정은 기존 취소 후 신규 생성 방식이며 ID가 바뀝니다. 응답을 잃었다고 무조건 다시 수정하지 않습니다. 기존 ID와 목록을 확인해 새 ID를 확정하고 이전·새 ID 관계를 저장합니다. 후보를 유일하게 식별하지 못하면 보류합니다. 한 요청의 멱등성 보장과 기존 ID 404의 의미는 고정 명세·FAQ를 함께 확인합니다.

## WebSocket과 계좌 동기화

주문 이벤트의 무손실 보장은 연결 세션 내부에 한정됩니다. 단절 구간은 재전송되지 않습니다. 재연결 후 구독을 복구하고 OPEN·필요한 CLOSED 페이지·관리 중 주문·보유 자산을 재동기화합니다. 이벤트 버퍼와 스냅샷의 겹침으로 상태가 과거로 돌아가지 않도록 연결 세대와 로컬 상태 버전을 사용하고, 필요 시 재조회합니다.

수신 이벤트 보존·큐 포화는 [R2 보존 계약](architecture.md#이벤트-보존과-수신-큐)을 따릅니다. 과거 관측 누락과 현재 상태 복구를 분리하며, REST 동기화로 이벤트 이력이 완전해졌다고 표시하지 않습니다. 이벤트 prune은 P4 승인·제출·미확정 기록·감사 저널과 별개의 보존 정책이며 이 기록들을 함께 삭제하지 않습니다.

REST 조회도 계좌 전체의 원자적 스냅샷이 아닙니다. 앱·WTS의 동시 주문, 조회 범위 밖의 주문, 조회 직후의 체결이 존재할 수 있습니다. 불일치가 해소되지 않으면 신규 쓰기를 제한하며 가짜 exactly-once·원장 완전성 보장을 하지 않습니다.

## 비상 중단

`pause`는 신규 실제 쓰기 디스패치를 중단합니다. 이미 전송 중인 요청의 성공을 철회하거나, 미체결·조건주문을 취소하거나, 보유 종목을 매도하지 않습니다. 재개는 소유자가 준비 상태·미확정 작업을 확인한 뒤 수행합니다. 주문·조건주문 취소는 각각의 승인 작업으로 제공합니다.

## 기록과 외부 데이터

기록에는 누가 어떤 초안을 승인했고 어떤 정책·조회 상태로 요청했는지, 시도·응답·토스 참조 ID와 결과를 남깁니다. 일반 로그는 correlation ID 중심으로 마스킹하고, 필요한 민감 기록에는 접근·보존 기간을 설정합니다. SQLite 자체 암호화를 자동 보장한다고 설명하지 않습니다. 로컬 디스크 보호·백업 접근도 운영 범위에 포함합니다.

토스 FAQ의 본인 매매 목적·제3자 배포 제한과 AI 처리 범위는 별도로 확인해야 합니다. 계좌·시세 데이터를 외부 모델에 전달하는 허용 범위와 사용자가 동의한 데이터 최소화 정책을 실제 연결 전에 결정합니다. 키를 숨기는 것만으로 데이터 처리 동의가 해결되지 않습니다.
