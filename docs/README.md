## 계약의 우선순위

사용자의 후속 지시는 이 기준안을 변경할 수 있습니다. 변경 시 관련 문서를 함께 갱신합니다. 공식 API의 실제 요청·응답 형식은 고정한 upstream 명세가 기준이며, 우리 서버의 권한·승인·운영 동작은 요구사항과 주문 설계가 기준입니다. 문서와 명세가 충돌하면 충돌을 기록하고 해소한 뒤 구현합니다.

API 대응 데이터는 어떤 기능이 구현·검증됐는지 나타냅니다. 행 개수만으로 완료를 판단하지 않습니다. 자세한 기능 설명은 API 지원 계약을 따르고, 대응 데이터와 사람이 읽는 표는 일치시킵니다.

## 용어

| 용어 | 의미 |
|---|---|
| 서버 | 토스 연결과 MCP 등을 제공하는 단일 애플리케이션 프로세스 |
| MCP | AI가 서버 도구를 발견하고 호출하는 프로토콜 |
| CLI | 설정·서버 실행·진단과 서버 업무 호출을 위한 실행 인터페이스 |
| upstream | 토스증권이 제공하는 공식 API와 명세 |
| 원본 클라이언트 | upstream 요청·응답을 처리하는 서버 내부 코드 |
| 승인 작업 | 내용이 고정된 초안과 사용자 승인에 연결된 쓰기 요청 |
| 동기화 | REST 조회와 수신 이벤트를 사용해 로컬 상태를 맞추는 작업 |
| 전체 지원 | 명세의 전체 업무 기능과 주요 조건·오류·복구가 구현·검증된 상태 |

## 상태 표기

- `planned`: 계약만 작성됐습니다.
- `implemented`: 코드가 있으나 해당 기능의 수용 검증이 끝나지 않았습니다.
- `verified`: 고정 명세를 기준으로 필요한 모의·계약 검증이 통과했습니다. 실계좌 검증을 의미하지 않습니다.
- `live-verified`: 사용자가 허용한 범위의 실제 환경 검증 기록이 있습니다. 계좌별 거래 자격까지 보장하지 않습니다.
- `blocked`: 구체적 외부 조건 때문에 수행할 수 없는 기능입니다. 사유와 해소 조건을 기록합니다.

`readonly`와 `trading`은 시작 프로필이며 구현 상태와 별개입니다. `toss`와 `mock`는 backend입니다. 기본값은 `toss + readonly`이고, 개발은 명시적인 `mock + readonly`로 수행합니다. R1은 REST 조회, R2는 실시간을 더한 조회 전체, T1은 선택적 주문 전체를 의미합니다. 전체 기능이 구현되어도 기본 프로필은 readonly입니다.
