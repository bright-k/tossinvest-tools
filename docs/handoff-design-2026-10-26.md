## 구현 기준 요약

- 프로젝트·실행 파일 `tossinvest-tools`, 서버 표시 `TossInvest Tools Server`, MCP 등록 `tossinvest`, 도구 접두사 `tossinvest_`.
- Go 단일 서버, `net/http`, 공식 Go MCP SDK, SQLite·Decimal 기준안.
- Codex의 수명과 독립된 서버를 `127.0.0.1:17840`에서 실행하고 `/mcp` 제공.
- REST 1개 인증은 내부, 34개 조회는 도구, 6개 쓰기는 준비 도구와 공통 승인 실행으로 대응.
- `serve` 또는 `serve --mode=readonly`는 주문 준비·실행 도구를 등록하지 않고 서비스·broker 전송에서도 막음. 주문 도구는 `--mode=trading` 명시 시작에서만 선택적으로 포함.
- mode는 프로세스 시작 시 고정. 설정·이전 DB·MCP로 승격하지 않음. 실제/모의 연결은 별도 `--backend=toss|mock`이며 기본 toss, 개발은 명시적 mock.
- 별도 AsyncAPI의 체결·호가·주문 이벤트, 구독·ACK·PING·재연결·동기화까지 전체 지원.
- readonly 기본, 실제 비밀은 사용자 로컬 등록. 모델의 승인 플래그와 도구 접속 토큰은 소유자 승인 증거가 아님.
- readonly 재시작의 미확정 거래 복구도 조회만 수행. 주문 승인·격리·거래 DB 미구현이 readonly 준비·사용을 막지 않음.
- 원본 명세는 고정·보존하고 자동 갱신하지 않음. 생성기 호환 검증 전 라이브러리 선택을 완료했다고 쓰지 않음.
- 계좌 허용은 빈 집합에서 시작. setup accounts가 같은 서버의 UID 검증 소유자 소켓으로 별칭·scope 연결을 적용하고, MCP에는 마스킹·허용 계좌만 반환. 권한 철회는 upstream 장애에도 가능.
- 처음 보는 주문 ID는 허용 계좌의 단건 GET으로만 확인하고 확인된 타 계좌 ID는 사전 거부. 다른 계좌 fallback·404로 소유 추정 금지. R-006의 사전 거부 문구를 이 구분에 맞게 조정.
- mock는 실행별 credential·분리 DB·0600 접속 파일을 사용하고 실제 Keychain은 사용하지 않음. 실제 backend credential과 섞지 않음.
- R2 수신 이력은 7일·계좌당 100,000건·전체 payload 256 MiB, 주문 큐는 1,024건·8 MiB·1초 한도. 만료 커서는 CURSOR_EXPIRED, 포화는 gap/복구. P4 저널에는 이 prune 정책을 적용하지 않음.

## 조회용 계약 기본안 반영 — 2026년 10월 26일

- 사용자의 후속 요청으로 위 네 발견 사항의 문서상 기본안을 채택했다. 과거 검토 기록의 미해결 판정은 그 당시 상태이며, 현재 결정은 [ADR 0004](decisions/0004-readonly-access-and-event-history.md)와 [접속 계약](interfaces.md)·[보존 계약](architecture.md#이벤트-보존과-수신-큐)을 따른다.
- 요구사항 R-006·R-016·R-025, 보안·실행 프로필·운영 안내·API coverage·구현 계획·검증 계획을 맞췄다. 대응 데이터의 17개 행에는 선택 필드 contract_reference를 추가했으며 upstream 작업/도구 수·available_modes·상태는 바꾸지 않았다.
- 수용 검증은 기존 T-001~T-038에 T-039~T-044를 추가했다. R1은 계좌 선택·철회·ID·mock 인증, R2는 보존·커서·큐 포화 검증이다. 이는 검증 계획이며 아직 테스트 코드나 통과 증거가 아니다.
- 정적 검증: Markdown 22개·상대 링크/anchor 102개·JSON 4개·원본 해시/크기/버전/ref 431개·REST 41개/WS 10개 대응·contract_reference 17개·35/39/47개 계획 도구·요구사항 37개와 수용 시나리오 44개의 ID/참조를 확인했다. 수정 문서의 공백·충돌 마커와 git diff --check도 확인했다. 이는 애플리케이션 테스트가 아니다.
- 바로 다음 작업은 P0 그대로다. P1~P2/P3에서 새 계약을 구현하고 수용 기준을 검증한다. 실제 단건 API의 계좌 제한은 모의 계약과 별도 허용된 실계좌 조회로 확인하고, 확인 전 live-verified로 처리하지 않는다.
- 코드·의존성·키 등록·실제 조회·서비스 설치·주문·commit·push는 수행하지 않았다. 문서 기본안 채택과 구현 완료를 구분한다.

## 구현 목표 전달 검토 — 2026년 10월 26일

- 현재 계약은 P0~P3의 readonly R1·R2 구현을 맡기기에 충분하며 새 구조 결정을 선행할 필요는 없다. 목표 문안은 사용자 설정 후 실제 조회할 수 있는 구현, 키 없는 모의 수용, 실제 MCP 클라이언트 접속 증거를 명시해야 한다.
- R2 구현·모의 검증 완료, 대상 에이전트 클라이언트 호환 확인, 사용자 설정 후 실제 계좌 조회 확인은 서로 다른 결과다. SDK 클라이언트만의 성공을 대상 에이전트 앱의 성공으로 확대하지 않고 클라이언트 이름·버전·실행 환경을 남긴다. 등록·세션 갱신을 사용자가 해야 한다면 그 마지막 단계와 미확인 범위를 명시한다.
