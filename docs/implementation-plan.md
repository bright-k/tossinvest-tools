# 구현 계획

먼저 readonly로 사용할 수 있는 결과를 완성합니다. R1은 P0~P2의 REST 조회 서버, R2는 P3의 실시간·로컬 운영까지 갖춘 조회 전체입니다. 선택적 T1은 P4 이후의 주문 전체입니다. 주문 승인·실주문 격리의 미정 사항은 R1·R2를 막지 않습니다. 최종 공식 API 전체 지원 범위는 유지합니다.

2026-10-26 현재 P0~P3 readonly R1/R2를 구현하고 모의 수용 검증을 완료했습니다. 실계좌·사용자 Keychain UX·실제 서비스 설치와 이 채팅의 MCP 재연결은 별도 대기입니다. P4 이후 주문 모듈은 미착수이며 이번 실행 파일은 trading 시작을 거부합니다. 실제 진행 현황은 [인수인계](handoff.md)와 [API 대응 데이터](api/operations.json)에 갱신합니다.

## P0 명세와 도구 호환성

| 작업 | 산출물 | 종료 기준 |
|---|---|---|
| Go 도구체인과 의존성 검증 | Go 모듈, 고정 버전, 도구 실행 방법 | 지원 중인 Go와 공식 MCP SDK·생성기가 함께 빌드됨 |
| 실제 OpenAPI 코드 생성 | 생성 설정과 재현 가능한 생성 명령 | 원본 41개 작업의 요청·응답 코드가 생성·컴파일됨 |
| 스키마 특수 형식 검증 | 필요한 adapter·overlay와 테스트 | form 인증, oneOf·allOf·null·Decimal·오류 예제가 손실 없이 처리됨 |
| 범위 자동 검사 | 명세·manifest·operations 대응 검사 | 41개 REST·10개 WS 작업의 누락·중복·해시 불일치를 검출함 |
| 최소 MCP 호환성 | 모의 도구의 로컬 HTTP 연결 | 현재 클라이언트와 프로토콜 협상·발견·호출·오류를 확인함 |
| 결정 기록 | ADR 0001과 인수인계 갱신 | 선택한 버전·한계·후속 검증을 기록함 |

이 단계에는 실제 키와 토스 계좌가 필요 없습니다. 생성기가 원본을 다루지 못하면 원인을 최소 예제로 분리하고 adapter·생성기 대안을 비교합니다. 원본을 몰래 3.0으로 낮추거나 널·필수 필드를 삭제하지 않습니다. 작은 보정으로 해결할 수 없는 경우에만 ADR의 기술 선택을 재검토합니다.

## P1 조회 코어와 로컬 연결 기반

- 설정 schema, mode/backend, 로컬 경로, 단일 인스턴스, health·기능별 준비 상태와 종료 처리를 구현합니다.
- 프로필별 불변 capability registry와 공통 서비스·broker 전송 검사를 구현합니다. 기본 readonly이며 `--mode=trading` 미구현 요청은 명확히 거부합니다.
- 모의 토스 adapter와 SecretStore interface를 두고 실제 비밀 없이 실행합니다.
- 토스 SecretStore와 MCP credential provider를 분리하고 mock 전용 DB·실행별 credential·고정 파일 경로와 소켓을 준비합니다. Keychain·toss credential 접근이 없는 인증 실패 경로를 검증합니다.
- P0에서 생성한 REST 전체 typed client 중 인증과 34개 조회를 공통 헤더·오류·timeout·호출 제한에 연결합니다. 생성된 6개 쓰기 메서드도 readonly에서 호출할 수 없게 합니다.
- 토큰 갱신 single-flight와 내부 계좌 매핑을 구현합니다.
- 빈 허용 집합·주체 scope·access_revision과 ID의 unknown/confirmed/conflict 관계를 구현합니다. unknown 조회는 허용 계좌의 단건 GET으로만 확인하고 타 계좌 fallback을 금지합니다.
- R1에 필요한 SQLite metadata·계좌 매핑·동기화·cache만 구현합니다. 초안·승인·제출 저널은 P4에서 추가합니다.
- macOS Keychain adapter와 비밀 없는 설정, 최소 권한 MCP 접속 credential 준비·helper 경계를 구현합니다. 기본 테스트는 fake이고 OS 연동 검증은 별도 opt-in으로 합니다.
- 인증·34개 조회의 직렬화·응답·주요 실패와 readonly에서 6개 쓰기 전송이 전혀 발생하지 않는지 검증합니다.

종료 기준은 키 없는 mock 실행, 인증·조회 코어, 토큰 갱신·종료·DB 실패·모드 차단 검증입니다. 승인 서비스·실주문 전용 schema·전체 쓰기 계약 검증을 P1의 선행 조건으로 두지 않습니다.

## P2 조회용 MCP와 CLI 수명 관리

- 34개 조회 업무를 MCP 도구에 연결하고 모든 원본 query/path 기능을 타입·계좌 권한과 함께 제공합니다.
- 공통 결과 metadata와 오류 코드, 페이지네이션을 정의합니다.
- [접속과 결과 계약](interfaces.md)의 상태·metadata·오류·exit code를 schema와 테스트로 고정합니다.
- 계좌/종목·주문 ID 접근 검사, loopback·Host·Origin·MCP 토큰 검증을 구현합니다.
- setup·serve·doctor·status·mcp-auth-header의 모의 실행과 종료 코드를 구현하고, 실제 연결은 사용자가 로컬 설정할 수 있게 준비합니다.
- setup accounts의 UID 검증 소켓·60초 발견 세션·별칭·grant 집합 교체·철회와 get_accounts 마스킹을 구현합니다. 설정 JSON이나 MCP로 계좌 권한을 바꾸지 못하게 합니다.
- T-039~T-042로 초기 계좌 비노출·revision 경합·앱 신규 ID·mock 인증·재시작을 검증합니다. [ADR 0004](decisions/0004-readonly-access-and-event-history.md)의 문서 결정을 실제 동작으로 확인합니다.
- Codex 로컬 접속 인증 저장 방식·MCP 등록 예시를 실제 연결 결과로 갱신합니다.
- readonly의 tools/list에 34개 조회와 서버 상태만 등록합니다. 준비·실행·정정·취소·조건 변경의 미등록·직접 호출 차단·실제 전송 차단을 검증합니다.

종료 기준은 R1 조회 전용 사용 가능입니다. 현재 클라이언트의 발견·호출, 34개 조회의 계약·권한·입력, Keychain·접속 bootstrap을 검증합니다. readonly에서 거래 준비 미완료는 정상이며, 앱 주문·조건주문 내역도 조회합니다. 실제 조회 검증은 사용자가 허용한 연결 범위에서 `live-verified`로 구분합니다.

## P3 실시간 전체와 계좌 복구

- KR·US 체결·호가와 personal:order를 한 WS 관리자로 통합합니다.
- 전체 집합 선언, id echo, ACK 부분 거부, 오류 시 기존 집합 유지, PING·pong과 backoff를 구현합니다.
- 수신 경로의 backpressure를 제한하고 주문 이벤트를 신속히 기록합니다.
- [보존·수신 큐 계약](architecture.md#이벤트-보존과-수신-큐)의 7일/100,000건/256 MiB와 1,024건/8 MiB/1초 경계를 구현합니다. 포화·DB 실패는 gap과 재연결·겹침 동기화로 처리합니다.
- 최신 스냅샷·이벤트 조회·연결 상태·권한 있는 구독 변경 도구를 연결합니다.
- T-043~T-044로 prune watermark·MAC 커서·만료·재시작·권한 revision·보존과 저널 분리·큐 포화를 검증합니다. REST 복구 후에도 과거 관측 누락은 표시합니다.
- 단절·절전·재시작의 누락 구간과 REST 동기화, 중복·역순 반영을 검증합니다.
- 앱·WTS의 동시 주문과 API에서 보이지 않는 주문 유형의 한계를 결과에 반영합니다.
- macOS ARM64 실행 파일과 launchd readonly 설치·상태·중단·제거, 로그 순환·기본 백업·복구를 제공합니다. 운영 서비스는 사용자가 선택할 때만 설치합니다.
- query_ready와 streams_ready를 구분하고 주문 모듈 미구현으로 조회 서버 전체가 미준비가 되지 않게 합니다.

종료 기준은 R2 조회·실시간 전체와 로컬 운영입니다. AsyncAPI 10개 작업과 모든 변형·제한·복구를 검증하고, readonly에서 수신·동기화가 주문을 제출하지 않음을 확인합니다. 실주문 승인 UI나 trading 전용 계정은 필요하지 않습니다.

## P4 승인과 전체 쓰기 업무

P4는 선택적 주문 모듈입니다. R1·R2를 먼저 사용·배포할 수 있고, 당장 주 사용 목적이 readonly이면 이 단계는 후속 범위로 남깁니다.

이 단계의 처음에 독립 사용자 인증과 분리 실행 방식을 ADR 0002에 구체화합니다. 결정 전에도 모의 서비스·상태 전이·도구 스키마 개발은 가능합니다. 검증한 승인 증거·실행 경계가 없으면 실제 거래 활성화는 완료로 처리하지 않습니다.

- 6개 쓰기 업무의 준비 도구와 공통 승인 실행 도구를 구현합니다.
- `--mode=trading`에서만 준비·실행·pause를 등록하고, 같은 실행 파일의 readonly 프로필은 이전 기능 목록과 차단 경계를 유지합니다.
- R1·R2 DB에서 trading 저널·승인·예약을 additive migration으로 추가합니다. readonly 재시작의 복구는 조회만 허용합니다.
- 초안 정규화·해시·만료·정책 버전·사용자 확인·한 번만 소비하는 증거를 구현합니다.
- 한도·잔고·미체결·시세·시장·조건주문 제약과 고액 확인을 검증합니다.
- 전송 전 영속 기록, 생성 멱등키, 미확정 결과·재시작·유효시간 경계 복구를 구현합니다.
- 정정·취소의 결과 확인과 조건주문 수정의 신규 ID 추적을 구현합니다.
- 소유자 정책·pause·resume와 거래 활성화 권한을 AI 도구와 분리합니다.

종료 기준은 R-008~R-015, R-019, R-023~R-024의 주문 검증과 공격·실패 시나리오 통과입니다. 모든 쓰기 기능은 먼저 mock에서 검증합니다. 실계좌 자동 주문 테스트를 CI나 일반 개발 명령에 넣지 않습니다.

## P5 선택적 주문의 운영 강화

- macOS ARM64 빌드·버전 출력·포함 명세 버전·체크섬을 제공합니다.
- R1에서 구현한 Keychain·접속 인증에 trading 주체·소유자 승인·자격증명 회전의 운영 검증을 추가합니다.
- P3의 launchd에 명시적 trading 설치·준비 검증을 추가하고, 기본 재설치와 readonly 복귀가 과거 거래 플래그를 남기지 않게 합니다.
- 터미널 PATH에 의존하지 않는 실행 경로, 크래시 재시작 제한과 로그 순환을 적용합니다.
- SQLite 백업·복원·이전 실패와 저장소 접근 권한을 검증합니다.
- 실제 설치·실행 문서로 README와 로컬 운영 안내를 바꿉니다. 계획 명령을 그대로 성공 사례로 옮기지 않습니다.

종료 기준은 선택적 trading의 독립 승인·서비스·복구 검증입니다. 조회용 로컬 설치·운영은 이미 R2에서 사용할 수 있어야 합니다. 운영 서비스를 실제 사용자 PC에 설치하는 행위는 사용자의 명시적 실행 요청 범위에서만 합니다.

## P6 전체 지원과 릴리스 점검

- REST 41개 작업과 WS 10개 작업에 실제 검증 증거를 연결합니다.
- 각 작업의 입력 변형·오류·정책·원본 응답 처리를 확인합니다.
- 개발 명령·테스트·생성·명세 diff·마이그레이션·패키징 검사를 CI에 고정합니다.
- 라이선스·제3자 명세 포함 범위와 토스 데이터 이용 조건을 정리합니다.
- 거래 활성화의 한도·계좌·승인·분리 실행과 데이터 전송 정책을 소유자가 결정할 수 있도록 안내합니다.
- 릴리스 노트와 인수인계에 구현 완료·모의 검증·실계좌 검증을 구분합니다.

최종 완료는 모든 업무 기능의 verified 상태와 수용 기준 충족입니다. `live-verified`가 필요한 운영 기능은 별도 조건을 기록합니다. 실제 주문을 하지 않았다는 이유로 모의 계약 검증을 생략하거나, 모의 검증을 실제 운용 보증으로 확대하지 않습니다.
