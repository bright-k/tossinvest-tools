# 조회용 계좌 권한과 모의 인증·이벤트 보존

- 날짜: 2026년 10월 26일
- 상태: 채택·readonly R2 구현 및 모의 수용 검증 완료. 실제 사용자 Keychain/실계좌/운영 검증은 별도 대기.
- 관련 요구사항: R-004~R-007, R-014, R-016~R-017, R-020, R-023~R-025, R-028~R-029, R-034~R-036
- 기존 결정과의 관계: ADR 0001·0003을 구체화한다. ADR 0002의 독립 실주문 승인·격리 결정은 후속 P4에 유지한다.

## 맥락

후속 문서 검토에서 빈 설정의 계좌 선택, 로컬에 없는 앱 주문의 권한 판정, Keychain 없는 mock MCP 접속, 이벤트 보존과 커서 만료의 계약이 부족함을 확인했다. 사용자는 이 항목에 합리적인 기본안을 문서화하도록 요청했다. 실제 키 등록·계좌 조회·주문을 수행하라는 요청은 아니다.

## 결정

계좌 허용은 기본 거부다. 초기 주체 codex-readonly는 상태·시장·계좌 조회와 R2 스트림 조회/구독 관리 scope를 갖되 허용 계좌는 비어 있다. `setup accounts`가 동일 UID 전용 Unix socket을 통해 실행 중인 서버에서 계좌를 발견하고, 소유자가 마스킹된 목록에서 별칭과 허용 집합을 선택한다. 서버가 원자적으로 grant와 access_revision을 갱신하고 MCP에는 허용된 별칭·유형·마스킹 표시만 반환한다. 이 로컬 경계는 같은 UID의 에이전트 셸에 대한 격리나 주문 승인 증거가 아니다.

ID를 모른다는 이유로 앱에서 생성된 주문을 거부하지 않는다. 명시한 계좌 허용을 먼저 확인하고 unknown 주문·조건 ID는 해당 계좌 헤더를 주입한 단건 GET으로만 확인한다. 확인된 타 계좌 ID는 사전 거부하고, 404·통신 실패로 소유 관계를 추정하지 않는다. 다른 계좌로 fallback하지 않는다. R-006의 종전 사전 거부 문구를 이 구분에 맞게 수정한다. upstream 계좌 제한은 검증할 전제이며 전제 불충족 시 해당 단건 경로를 차단하고 보수적인 목록 기반 adapter를 검토한다. 쓰기는 fresh 상태·확정 관계·승인을 별도로 요구한다.

mock도 인증한다. 실제 SecretStore와 로컬 MCP credential provider를 나누고, mock 서버가 매 실행마다 난수 credential을 발급해 mock 전용 0600 파일과 메모리에만 둔다. helper는 backend와 run_id가 일치할 때만 이 credential을 읽는다. 실제 Keychain·실제 credential·toss DB를 재사용하지 않는다. 재시작마다 credential이 바뀌며 인증을 생략하는 fallback은 없다.

주문 수신 이력은 7일·계좌당 100,000건·전체 payload 256 MiB 중 먼저 도달한 한도로 보존한다. 주문 수신 큐는 1,024건·8 MiB·대기 1초를 상한으로 하며 포화는 gap 표시·연결 복구·REST 동기화로 처리한다. 시세는 구독별 최신 스냅샷으로 합친다. 보존 삭제는 P4 승인·제출·감사 저널에 적용하지 않는다. 커서는 주체·계좌·권한 revision·실행 run_id에 묶고, 삭제 범위 또는 이전 실행을 가리키면 CURSOR_EXPIRED를 반환한다. REST 동기화로 누락된 이벤트 이력이 복원됐다고 주장하지 않는다.

입력·오류·순서의 기준은 [접속 계약](../interfaces.md), 보존·큐의 기준은 [구조 설계](../architecture.md#이벤트-보존과-수신-큐), 사용자 절차는 [로컬 운영](../local-operation.md)이다. 한도는 upstream 사실이 아닌 이 서버의 초기 정책이며 변경 시 해당 계약과 검증을 함께 갱신한다.

## 대안

| 대안 | 이번에 선택하지 않은 이유 |
|---|---|
| 발견한 계좌를 전부 자동 허용 | 사용자가 선택하지 않은 자산·주문이 모델에 노출될 수 있다 |
| CLI가 별도 토큰으로 계좌 발견 | 단일 토큰 관리자 계약을 깨고 기존 토큰을 무효화할 수 있다 |
| R1부터 독립 승인 UI 완성 요구 | 조회 설정을 실주문 인증 결정에 종속시킨다 |
| 모든 미확인 ID 거부 또는 전체 계좌 탐색 | 유효한 앱 주문을 막거나 권한 범위를 넘어선 조회를 만든다 |
| mock의 무인증·공용 정적 credential | 실제 인증·권한 실패 검증을 생략하게 된다 |
| mock도 실제 Keychain에 저장 | 기본 검증의 OS 비밀 저장소 독립성을 잃는다 |
| 무제한 이벤트 저장·만료 커서에 빈 성공 반환 | 디스크 증가를 제한하지 못하거나 누락을 숨긴다 |
| 재시작 후에도 커서 유지 | 복원·이전·세대 검증이 복잡해진다. 초기에는 보존 범위 재조회와 중복 가능성을 명시한다 |

## 결과와 검증 조건

P1~P2는 계좌 선택 소켓·grant/revision·명시적 account_alias·ID 관계·mock credential을 구현한다. P3는 제한된 큐·보존 watermark·커서 MAC·만료와 복구를 구현한다. R1·R2를 주문 승인 UI·거래 저널 설계에 종속시키지 않는다.

[검증 계획](../testing.md)의 T-039~T-044로 빈 설정·철회 중 in-flight·앱 신규 주문·교차 계좌·mock 파일/재시작·보존 경계·큐 포화·DB 실패를 검증한다. 수치 한도의 적절성은 fake clock·모의 부하로 확인하고, 실제 upstream 계좌 제한은 별도 허용된 조회 기록으로 남긴다. 동일 UID 소켓은 실주문 격리 검증을 대신하지 않는다.

구현과 T-039~T-044의 현재 증거는 [검증 기록](../verification/README.md)에 있다. 별칭 tombstone을 유지해 다른 계좌로 재할당하지 않으며, 이름 변경은 기존 grant 철회 후 명시적 발견/선택으로만 적용한다.
