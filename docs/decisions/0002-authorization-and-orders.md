# 서버 승인과 주문 실행 경계

- 날짜: 2026년 10월 26일
- 상태: 선택적 trading의 보안 기준안. readonly R1·R2의 선행 조건이 아니다. 실주문 단계에서 독립 사용자 인증과 분리 실행 방식을 구체화한다.
- 관련 요구사항: R-006, R-008~R-015, R-017~R-020, R-023~R-025, R-029~R-030

## 맥락

토스 키를 모델에게 보이지 않게 하더라도 무제한 주문 도구를 제공하면 손실을 제한할 수 없습니다. MCP·CLI·승인 화면이 서로 다른 정책을 가지면 우회가 생깁니다. 토스 멱등키는 시간 제한이 있고, WS 단절 동안의 주문 이벤트는 재전송되지 않습니다.

## 결정

서버가 정규화한 초안·내용 해시·계좌·주체·정책 버전·만료와 사용자 승인 증거를 저장합니다. 모델은 초안 생성·조회·승인된 작업 실행만 요청합니다. `confirm=true`나 자연어를 사용자 인증으로 취급하지 않습니다.

모든 쓰기에 같은 권한·한도·승인 검사를 적용합니다. 정정·취소·조건주문도 포함합니다. 토스 비밀과 MCP 접속 자격증명을 분리하고 소유자 정책 변경·모드 전환·승인 증거 발급을 AI 권한 밖에 둡니다.

승인 소비·한도 예약·전송 의도를 DB에 커밋한 뒤 네트워크 요청을 보냅니다. 결과가 불명확하면 기록된 ID와 내용으로 안전하게 복구합니다. 유효시간이 지났거나 원본이 멱등성을 보장하지 않는 경우 자동 재전송하지 않습니다. 주문 이벤트와 REST 동기화를 결합하고 누락 없는 원장·무조건 exactly-once를 보장하지 않습니다.

기본 모드는 readonly입니다. 실제 쓰기 전에 별도 서비스 계정 또는 독립 호스트, 소유자 확인 수단, 한도와 정책을 결정합니다. 로컬 같은 사용자 아래에서 Keychain과 bearer token만 둔 상태를 강한 격리로 부르지 않습니다.

## 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 모델이 confirm 플래그를 재전송 | 사용자가 정확한 내용에 동의했다는 서버 측 증거가 없음 |
| 모든 API를 범용 HTTP 도구로 노출 | endpoint별 권한·입력 조합·승인 경계를 검증하기 어려움 |
| CLI는 주문 제한에서 제외 | 모델 또는 스크립트가 별도 경로로 우회할 수 있음 |
| 타임아웃이면 새 주문 ID로 재시도 | upstream이 이미 처리한 주문을 중복 생성할 수 있음 |
| WS 이벤트만을 최종 원장으로 사용 | 단절 구간이 재전송되지 않고 모든 채널 주문을 영구 보장하지 않음 |

## 남은 결정

P4 시작 시 사용자 확인 수단과 실행 격리 방식을 ADR에 추가합니다. 초기 후보는 로컬 소유자 화면과 사용자 존재 확인, 별도 서비스 계정 또는 독립 호스트입니다. 선택한 방식이 모델의 셸·브라우저 권한으로 우회되지 않는지 확인합니다. 인증 수단을 결정하기 전에도 모의 승인 상태 머신과 정책 검증은 구현할 수 있습니다.

실거래 한도·계좌·종목 정책과 AI로 전달할 데이터 범위는 소유자 설정입니다. 기본 미설정 상태에서 실제 쓰기를 허용하지 않습니다. 사용자에게 불필요한 반복 승인을 추가하지 않고, 유효한 동일 초안의 안전한 재시도는 서버가 기존 승인과 전송 기록에 따라 처리합니다.

자세한 상태 전이와 복구 계약은 [주문 처리](../security-and-orders.md)를 따릅니다.
