# 조회 전용 우선 배포와 시작 프로필

- 날짜: 2026년 10월 26일
- 상태: 사용자 후속 요구를 반영한 구현 기준
- 관련 요구사항: R-018, R-020, R-028, R-033~R-037

## 맥락

사용자는 실제 주문을 일으키는 명령의 포함 여부를 서버 실행 시 선택하고, 우선은 조회 전용으로 주로 사용하려고 합니다. 기존 문서의 기본 readonly와 쓰기 거부만으로는 도구 등록·실행 옵션·서비스 재시작·구현 순서를 한 가지로 결정하기 어렵습니다.

## 결정

단일 실행 파일에서 `serve --mode=readonly|trading`으로 프로필을 선택합니다. 생략은 항상 readonly이며, `--backend=toss|mock`으로 실제 연결과 모의 연결을 별도 선택합니다. 컴파일 feature flag나 실행 파일 분리는 초기 범위에 추가하지 않습니다.

readonly는 주문 준비·실행·정정·취소·조건주문 변경 도구를 등록하지 않고 공통 서비스와 broker 전송에서도 막습니다. 인증·구독·로컬 캐시 쓰기는 계좌 쓰기와 구분합니다. 모드의 실행 중 승격은 없고 재시작이 필요합니다. trading을 선택해도 사용자 승인·한도·상태 검증을 유지합니다.

처음 사용 가능한 결과는 R1 REST 조회 서버이며 R2에서 실시간 전체와 로컬 서비스를 갖춥니다. Keychain과 접속 인증은 R1 전에 구현합니다. 주문 모듈·승인 UI·실주문 격리를 R1·R2의 의존성으로 두지 않습니다. 전체 API 지원이라는 장기 목표는 유지합니다.

## 결과와 검증

초기 사용에 필요 없는 주문 도구가 AI 목록을 차지하지 않으며, 키 존재·설정 파일·예전 DB가 권한을 승격시키지 않습니다. readonly로 다시 시작하면 이전 미확정 요청도 조회만 수행합니다. launchd 자동 재시작은 설치할 때 명시적으로 선택한 argv를 사용합니다.

mode/backend 조합, tools/list, 직접 호출, CLI·운영 API, 원본 전송 차단, 과거 trading DB 복구와 서비스 등록을 검증합니다. 자세한 계약은 [실행 프로필](../runtime-profiles.md)을 따릅니다.

## 대안

| 대안 | 이번에 선택하지 않은 이유 |
|---|---|
| 주문 도구를 항상 보여 주고 실행 때만 거부 | 사용자가 요청한 조회 전용 제공 범위가 불명확하고 불필요한 도구가 노출됨 |
| JSON의 trading.enabled만으로 시작 권한 결정 | 과거 설정·환경·설정 갱신이 다음 실행을 암묵적으로 승격할 수 있음 |
| readonly/trading 별도 실행 파일·build tag | 초기 배포·검증 조합을 늘리며 현재 요청에는 런타임 선택으로 충분함 |
| 승인·주문 기능이 완성될 때까지 조회 배포 보류 | 우선 조회 전용으로 사용하려는 목표에 맞지 않음 |
