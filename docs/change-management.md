# 변경 관리

요구사항·공식 명세·구현·검증·운영 문서를 같은 변경 단위로 유지합니다. 문서만 갱신하고 구현 상태를 앞당기거나, 구현을 바꾸고 계약을 그대로 두지 않습니다. 일반 구현·수정·모의 검증은 사용자가 요청한 범위 안에서 진행합니다.

## 변경별 갱신 범위

| 변경 | 함께 확인할 자료 |
|---|---|
| 제품 범위·사용 흐름 | 요구사항 ID, 구현 계획, 수용 테스트, README |
| upstream API·명세 | 원본과 manifest, operations, coverage, 생성 코드·overlay, 계약 테스트 |
| MCP 도구·CLI·운영 API | 이름·입출력·오류·권한·호환성, 사용 예시와 통합 테스트 |
| 인증·승인·정책·재시도 | 보안 문서, ADR, 위협·장애 검증, 운영 안내 |
| 프로필·기능 등록·backend | runtime-profiles, operations의 available_modes/broker_effect, tools/list·직접 호출·재시작 검증 |
| DB·파일·설정 | 버전과 migration, 백업·롤백, 복구 테스트 |
| 의존성·Go 버전 | 고정 버전, 재현 가능한 생성·빌드, 호환성 검증, ADR의 전제 |
| 실제 완료 상태 | API 증거, 단계 상태, 인수인계, 릴리스 노트 |

모든 변경에 새 ADR을 요구하지 않습니다. 기존 결정을 바꾸거나 중요한 트레이드오프가 생길 때 작성합니다. 소규모 버그 수정은 요구사항·동작·검증 증거를 해당 변경에 남깁니다.

## 작업 절차

1. 현재 Git 상태와 기존 사용자 변경을 확인합니다.
2. 영향받는 요구사항·API·도구·저장 데이터·운영 동작을 식별합니다.
3. 동작 변경과 완료 조건을 필요한 계약에 먼저 또는 구현과 함께 반영합니다.
4. 작은 단위로 구현하고 관련 실패·경계·권한 검증을 실행합니다.
5. API 대응 상태와 증거를 갱신합니다. 구현 실패·미확정 항목은 그대로 드러냅니다.
6. 사용자에게 바뀐 동작·실행한 검증·남은 제약을 전달하고 인수인계를 갱신합니다.

테스트가 통과한 뒤 이유 없이 같은 검증을 반복하거나 범위를 넓히지 않습니다. 새 변경·실패·미해결 위험이 생길 때 필요한 검증을 추가합니다.

## 공식 명세 갱신

원본 URL의 `latest`는 바뀔 수 있습니다. 버전 숫자만 비교하지 않고 원본 SHA-256과 의미 차이를 확인합니다.

1. 새 REST·AsyncAPI를 별도 임시 위치로 내려받습니다. 인증정보가 필요한 endpoint를 명세 내려받기 대상으로 사용하지 않습니다.
2. JSON 형식·문서 버전·내부 ref·공식 서버 origin을 확인합니다. REST와 WS 버전은 독립 기록합니다.
3. 기존 파일과 메서드·경로·operationId·파라미터·request/response schema·enum·오류·한도·설명을 비교합니다.
4. 추가·변경·삭제를 API 대응 데이터에 반영합니다. 기존 행의 검증이 유효한지 재평가하고, 영향받는 항목만 상태·증거를 갱신합니다.
5. 고정한 생성기로 재생성하고 overlay 필요성과 소멸 여부를 검증합니다.
6. 요청·응답·주문·실시간 의미에 맞는 테스트와 운영 설명을 갱신합니다.
7. 원본 파일·manifest·대응 목록·코드·검증·출처를 한 변경으로 남깁니다.

지원 작업 개수가 같아도 필드·조건·의미는 바뀔 수 있습니다. 단순 endpoint 수 일치나 생성 성공만으로 호환 갱신을 완료하지 않습니다. upstream에 새 기능이 생기면 미구현을 명시하며 기존 릴리스가 새 전체 명세를 지원한다고 표시하지 않습니다.

## 상태와 증거

`operations.json`의 상태는 [문서 안내](README.md)의 정의를 따릅니다. `verification_evidence`에는 실제 존재하는 저장소 상대 경로나 비밀이 없는 검증 기록을 넣습니다. 생성 코드 경로만으로 verified를 부여하지 않습니다.

인증 1개는 서버 내부 기능으로, 조회 34개와 승인 쓰기 6개는 업무 기능으로 추적합니다. 이 집계는 현재 스냅샷의 값이며 갱신 시 다시 계산합니다. MCP 추가 운영 도구 수와 upstream 작업 수를 혼동하지 않습니다.

## ADR

새 ADR은 다음 번호로 작성하고 상태·맥락·결정·대안·결과·검증 조건·관련 요구사항을 포함합니다. 과거 결정은 삭제하지 않고 대체 ADR을 연결합니다. 중요한 선택의 미해결 조건은 인수인계에 다음 행동과 함께 남깁니다.

프로토콜·언어·코드 생성기·저장소 변경, 사용자 승인 방식과 권한 경계, 원격 공개, 다중 인스턴스 실행 등은 ADR 대상입니다. 사소한 패키지 분리나 함수 이름 선택까지 승인 절차로 확대하지 않습니다.

## 버전과 호환성

초기 릴리스는 0.x SemVer를 사용합니다. upstream API 버전과 프로젝트 버전은 따로 표시합니다. 도구 이름·입출력·CLI·설정·DB의 변경 영향을 릴리스 노트에 기록합니다. 사용자 스크립트가 의존하는 계약을 바꿀 때는 이전 방식·마이그레이션 또는 명확한 오류를 제공합니다.

오류는 안정적인 로컬 코드, 재시도 가능 여부와 결과 확정 여부, correlation ID로 구분합니다. 예를 들어 권한 거부·승인 필요·승인 만료·정책 제한·준비 미완료·upstream 제한·결과 미확정은 서로 다른 결과입니다. 정확한 코드·exit code·schema는 첫 구현에서 테스트와 함께 고정합니다. HTTP timeout을 확정 실패 코드로 단순 변환하지 않습니다.

## DB와 실행 파일 갱신

DB·설정 schema에 버전을 부여합니다. migration은 순서와 적용 상태를 기록하고 실패 시 운영 가능한 상태를 보존합니다. 새 실행 파일이 모르는 더 높은 DB 버전을 만나면 조용히 열거나 초기화하지 않고 거부합니다.

업그레이드는 신규 쓰기 중단 → 진행 작업 기록·종료 → 일관된 백업 → migration과 실행 파일 교체 → 조회 전용 동기화 → 준비 확인 순서로 합니다. DB 역변환이 없으면 실행 파일만 이전 버전으로 바꾸는 롤백을 보장하지 않습니다.

백업 복원으로 과거 승인·제출 기록이 되살아나도 자동 재실행하지 않습니다. 실제 토스 상태와 대조하고 미확정 요청·발급 ID·정책 예약을 먼저 복구합니다. 실제 주문은 Git revert나 DB rollback으로 취소되지 않습니다.

## 문서와 코드 리뷰

검토자는 기능의 실제 trigger와 결과, 권한 경계, 실패 시 재시도·복구, 테스트 증거를 확인합니다. PR 설명은 최종 동작과 검증을 중심으로 작성합니다. 대화 이력이나 폐기한 대안은 결정 이유에 필요할 때만 남깁니다.

프로젝트 라이선스와 제3자 명세 포함 조건은 공개 릴리스 전에 결정합니다. 사용자가 요청하지 않은 라이선스 선언, Git push·배포·운영 자격증명 변경은 문서 정리 작업에 포함하지 않습니다.
